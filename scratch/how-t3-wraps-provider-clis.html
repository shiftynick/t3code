T3 Code · internals pamphlet

The CLIs
hold the keys.

How T3 Code rides Claude, Codex, and Cursor subscriptions without becoming an API proxy.

T3 Code is a GUI and an orchestrator. It is not a man-in-the-middle for Anthropic, OpenAI, or Cursor. When you hit send, the server starts (or resumes) a child process of the vendor CLI you already installed and logged into. That process spends the subscription. T3 only speaks a local protocol over stdin/stdout.

model

Bring-your-own-subscription means: install claude, codex, or cursor-agent; run their login command on the machine that hosts T3; then let T3 spawn that binary. Tokens stay in the CLI’s home directory / OS keychain. The T3 process never presents them to api.anthropic.com, api.openai.com, or api.cursor.com.

One turn, five hops

01 Client Web, desktop, or mobile dispatches thread.turn.start over the authenticated WebSocket RPC.
02 Orchestration Event-sourced engine persists the command. A reactor, not the UI, is allowed to touch a provider.
03 Adapter ProviderService resolves the thread’s instance and calls a generic startSession / sendTurn.
04 Child CLI Codex app-server, Claude Agent SDK subprocess, or cursor-agent acp — each on stdio.
05 Vendor cloud Only the CLI talks to the subscription backend, using credentials from codex login / claude auth login / agent login.
typed WS · packages/contracts command → event → reactor driver registry local JSON-RPC / SDK IPC not T3’s socket

Three wrappers, three dialects

Claude

claudeAgent

Not a long-lived JSON-RPC server. T3 embeds @anthropic-ai/claude-agent-sdk and points it at your claude binary.

Spawn
SDK query() with pathToClaudeCodeExecutable
Transport
Claude Code’s private IPC (SDK owns the subprocess)
Login
claude auth login
Auth isolation
CLAUDE_CONFIG_DIR — never override HOME (breaks the macOS keychain)
Health check
claude --version, then a no-prompt SDK init to read account / subscription
  1. resolve binary + config dir
  2. query({ prompt, options })
  3. preset system prompt: claude_code
  4. stream SDK messages → canonical events
  5. permission callbacks come back through T3 UI

Codex

codex

T3 spawns the official Codex CLI in app-server mode and speaks its JSON-RPC over the child’s stdio via effect-codex-app-server.

Spawn
codex app-server (+ optional launch args)
Transport
JSON-RPC on stdin/stdout
Login
codex login
Auth isolation
CODEX_HOME (default ~/.codex); shadow homes share history, swap auth.json
Health check
same app-server: initialize then account/read
  1. initialize as client t3code_desktop
  2. initialized notification
  3. thread/start or thread/resume
  4. turn/start
  5. listen for thread/started, turn/started, item deltas

Cursor

cursor

Cursor’s agent speaks the Agent Client Protocol. T3 is an ACP client; the CLI is the ACP agent. Auth method id is literally cursor_login.

Spawn
cursor-agent acp (optional -e <apiEndpoint>)
Transport
ACP JSON-RPC on stdin/stdout (effect-acp)
Login
agent login — not cursor-agent login
Auth isolation
whatever the Cursor CLI already stored; T3 just calls authenticate
Health check
agent about, plus ACP list_available_models
  1. initialize (protocolVersion 1)
  2. authenticate { methodId: "cursor_login" }
  3. session/new or session/load
  4. session/prompt
  5. extensions: cursor/ask_question, cursor/create_plan

The seam orchestration actually sees

Drivers are plain values in BUILT_IN_DRIVERS. Each one builds a ProviderInstance with a snapshot, an adapter, and a small text-generation helper. The adapter contract is the same for every vendor:

startSession · sendTurn · interruptTurn
respondToRequest · respondToUserInput
stopSession · streamEvents

That is why the chat UI does not know or care whether the thread is Claude, Codex, or Cursor. Approvals, streamed tokens, and session ids are normalized into ProviderRuntimeEvents, ingested by ProviderRuntimeIngestion, and projected into the thread the client already subscribed to.

Complexity is supposed to live at this adapter boundary. Codex’s collab sub-agents, Claude’s SDK message zoo, and Cursor’s ACP extensions all collapse into the same event names before they cross the wire.

What T3 does

  • Discover the binary on PATH or a configured path
  • Spawn it in the project cwd with a scoped env
  • Translate vendor events into orchestration commands
  • Relay approvals and user-input prompts back to the GUI
  • Checkpoint the git worktree around each turn

What T3 never does

  • Store or replay ChatGPT / Claude / Cursor session cookies as its own API key
  • Open an HTTPS connection to the model vendor on your behalf
  • Ship the vendor CLIs — you install them
  • Let the browser talk to a provider. The server is the execution boundary

Where the subscription actually lives

Provider You log in with T3 points the child at Second account
Claude claude auth login CLAUDE_CONFIG_DIR if set; otherwise Claude’s default config dir another config dir + login; do not rewrite HOME
Codex codex login CODEX_HOME (often ~/.codex) shadow home that keeps its own auth.json
Cursor agent login whatever cursor-agent already authenticated ACP authenticate with cursor_login

Login happens on the machine running the T3 server, not on the phone or laptop you browse from. A remote client is just another WebSocket subscriber. The child process, the tokens, and the model call all stay on the host.
